Data Preparation

Why This Page Exists

Every figure on the Market Baseline page comes from one table. This page documents how that table was built: what we pulled, what we kept, what we removed, and what we repaired. Anyone reading our conclusions should be able to judge how much weight the evidence can carry.

Data Source

All postings come from the MET Employability Career Match API (Boston University Metropolitan College (2026)), specifically the /api/v1/student/jobs/ endpoint, which returns active, deduplicated, student-visible job postings with employer, location, salary, occupation, and skill fields attached.

Requests are authenticated with a personal API key sent in an X-API-Key header. The key lives in a local .env file that is excluded from version control; the repository contains only .env.example with empty values.

We also evaluated the /job-facts/ endpoint, which the API documentation recommends for classroom analysis. It returned no rows for our industry, so the /jobs/ endpoint is our source.

Industry and Career Scope

Industry code NAICS 2022 — 523, Securities, Commodity Contracts, and Other Financial Investments and Related Activities (U.S. Census Bureau (2022))
Career pathway Business Intelligence / Data Analyst
Date window Postings published on or after 1 September 2025 (a rolling twelve-month window)
Extraction date 15 September 2026

The date window keeps the analysis current. Hiring requirements shift, and a posting from three years ago describes a market our target user is no longer applying into.

Scope revision: from NAICS 5221 to 523

Module 1 anchored this project to NAICS 5221, Depository Credit Intermediation. When we pulled the data in Module 2, that code returned 59 postings in total — not a first page, but the entire available universe — and only 13 of them carried salary information. That is not enough to support a salary distribution, a skill-gap analysis, or a scorecard in later modules.

We measured the neighbouring codes before deciding, counting both total postings and postings matching our career pathway:

Industry code Total postings Analytics-pathway postings
5221 Depository Credit Intermediation 59 27
5241 Insurance Carriers 7,573 1,507
52 Finance and Insurance (whole sector) 27,893 7,824
523 Securities and Investments 15,176 4,787

Within the whole Finance and Insurance sector, NAICS 523 accounts for roughly two-thirds of all analytics postings. Taking the sector as a whole would therefore have meant studying securities and investments anyway, but with a blurred label and an incoherent mix of employers. We chose the explicit code instead.

The career pathway, the product question, and the underlying argument did not change. Only the industry anchor moved, and it stayed inside Finance and Insurance.

Why a three-digit code

The assignment asks for four- or six-digit NAICS codes where possible. We tested 5231 and 5239, the four-digit codes beneath 523, and both returned zero rows: this dataset does not carry four-digit granularity for the securities subsector, though it does for insurance. NAICS 523 is therefore the most specific code available for the industry we selected.

Role Definition

The assignment allows title keywords, SOC or O*NET mappings, skills logic, or a combination, provided the choice is explained. We use a combination, for two reasons found in the data itself:

Job titles are inconsistent. Filtering on a single title such as “Data Analyst” returns a few hundred rows and discards obvious matches like Business Intelligence Analyst, Reporting Analyst, and Analytics Engineer.

The occupational coding is noisy. A large share of genuine analytics postings sit under the broad SOC “Management Analysts”, while some clearly unrelated roles carry the word “analyst” in the title. Neither signal is reliable on its own.

A posting is therefore kept when either condition holds:

  • its SOC name matches one of: data scientist, database architect, statistician, mathematician, operations research, market research analyst, financial and investment analyst, credit analyst, management analyst
  • or its title contains one of: analyst, analytics, data, business intelligence, BI, reporting, SQL, data science, machine learning

Information-security roles are then removed. They match the word “analyst” but belong to a different career pathway, and including them would distort the skill profile our product reports.

Derived Fields Added During Extraction

The API does not expose experience or education as structured fields, so three columns were derived from the posting text and one from a nested object:

Column How it was produced
skills_text Skill names flattened from a nested list into a semicolon-separated string
skills_count Number of skills attached to the posting
experience_years_raw First “N years” figure found in the description, by regular expression
education_level_raw Highest degree keyword found in the description (PhD, Master, Bachelor, Associate, High School)
organization_name Employer name lifted out of the nested organization object

The two _raw columns are a first pass. A posting that says “5 years of experience preferred, 3 years required” yields one number, and phrasing that does not follow the pattern yields nothing. They are treated as an approximate signal, not a measurement.

Cleaning Decisions

Cleaning is deliberately conservative. Where a value is implausible we blank it rather than guess a replacement, and where a whole posting is questionable we keep it and record the gap. Deleting rows narrows the sample; blanking a single field costs us only that field.

Duplicates. Postings are deduplicated on job_id. The API already returns a deduplicated feed, and no duplicates remained in our slice.

Rows with missing essentials. A posting is dropped if it has no identifier, title, employer, or publication date, because it cannot be attributed or placed in the date window. No rows failed this test.

A note on an error we caught here. The first cleaning run removed 932 of 6,199 postings as missing a publication date, while the source file showed that column fully populated. The cause was a parsing quirk rather than missing data: timestamps arrive in two shapes, some carrying fractional seconds and some not, and the date parser inferred a single format from the first values and rejected the rest. Setting the parser to accept any ISO-8601 timestamp restored all 932 rows. We mention it because a 15 percent silent loss would have skewed every figure downstream.

Dates. All dates are parsed to UTC. Where an expiry date fell before the publication date the expiry was blanked, since one of the two must be wrong and we cannot tell which. One posting was affected.

Salary. Reversed ranges, where the minimum exceeded the maximum, are swapped. Annual salaries below $10,000 or above $1,000,000 are blanked as data errors rather than genuine offers — 44 postings were affected. Postings without a salary keep every other field and are simply excluded from salary statistics. Hourly and annual figures are kept in separate columns and are not combined, because converting an hourly rate to an annual one requires an assumption about hours that the postings do not supply.

Experience and education. Left as extracted, with the approximation clearly labelled by the _raw suffix. They are usable for broad comparisons — whether a segment asks for more experience than another — but not for precise thresholds.

Skills. Stored as a semicolon-separated string with a count. Skill names are not yet normalised, so casing and synonyms (SQL, sql, Structured Query Language) remain distinct. That normalisation belongs to the skill-gap work in Module 3, where it has an analytical purpose.

Remote status. Reported exactly as the source provides it: remote, hybrid, onsite, or unknown. “Unknown” is kept as its own category and never folded into “onsite”, because an unlabelled posting is not evidence of an onsite role.

Location. Text fields are trimmed of stray whitespace. ZIP codes are padded to five digits and the placeholder 00000 is treated as missing. Coordinates outside the latitude and longitude bounds of the United States are blanked rather than deleted, so the posting survives with its other fields intact.

Industry and occupation codes. Kept as provided. The industry codes in this dataset are aggregated rather than plain NAICS 2022 codes, which is recorded in the data dictionary so no one later mistakes them for official codes.

Text and types. HTML markup and repeated whitespace are stripped from descriptions. Every column is then cast to an explicit type — dates, booleans, integers, floats, and categories — so that later analysis cannot silently treat a number as text.

Data Quality and Limitations

Coverage in the cleaned analytical panel, 6,199 postings:

Field Populated Share
Occupation code (SOC) 6,092 98%
Skills listed 5,742 93%
Remote status known (not “unknown”) 2,992 48%
Experience signal found 4,093 66%
Education signal found 3,675 59%
US state code 1,761 28%
Annual salary 1,206 19%
Hourly salary 258 4%

Three limitations follow, and they shape how the Market Baseline page should be read.

Salary coverage is low, and it is not specific to our industry. We checked the whole Finance and Insurance sector and found the same pattern everywhere, so this is a property of the source data rather than a consequence of our scope. Any statement about pay in this project describes the roughly one posting in five that discloses pay — a self-selected group that may skew toward larger or more regulated employers.

Geography is thin. Fewer than three postings in ten carry a US state code, and a substantial number of postings are outside the United States altogether. Location analysis is therefore restricted to postings that identify a state, and the counts behind each state are much smaller than the headline row count suggests.

Remote status is frequently unrecorded. Roughly half of postings are labelled “unknown”. Any remote-versus-onsite comparison describes the labelled half only.

By contrast, occupation codes and skill lists are close to complete, so the skill-gap work planned for Module 3 rests on firmer ground than the compensation analysis does.

Reproducing This Step

  1. Copy .env.example to .env and add a MET Employability API key
  2. pip install -r requirements.txt
  3. python notebooks/10_build_dataset.py — extraction and filtering
  4. python notebooks/12_data_cleaning.py — cleaning, typing, and the analytical panel
  5. python notebooks/14_data_dictionary.py — data dictionary

All work runs on the course AWS EC2 environment.
